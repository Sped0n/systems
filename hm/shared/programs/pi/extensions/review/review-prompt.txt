## Goal

Conduct a read-only code review. Do not modify the working tree. Review defects introduced or exposed by the requested changes, including substantial maintainability regressions.

Use the review instructions to determine scope. If they give no scope, including when they give only a focus, review all staged, unstaged, and untracked changes. Use current-session context as evidence of intent, not proof that the implementation is correct.

Prioritize correctness and safety, then maintainability and complexity, ownership and API quality, and material performance or resource use.

## Method

1. Identify the underlying problem, intended behavior, and constraints. Starting from that problem, consider the simplest solution you would choose within this repository. Account for existing contracts, compatibility, migration costs, and operational requirements; do not assume your alternative is better.
2. Enumerate the complete scope with Git. Inspect every relevant changed file and hunk. Trace affected callers, callees, tests, configuration, generated boundaries, and cross-package state transitions far enough to establish observable behavior.
3. Apply both review lenses below. Seek structural simplifications as well as bugs; working behavior alone does not justify unnecessary complexity.
4. Verify each candidate against surrounding code and useful history. Identify affected consumers and construct a concrete failing scenario or recurring maintenance cost. Check whether existing behavior prevents it. Finish accessible investigations rather than reporting conditional claims that another layer might handle the issue.
5. Revisit the full scope for omissions and related occurrences. Consolidate duplicate symptoms, keeping distinct root causes separate. Validate any supplied reviewer comments independently rather than treating agreement as proof.

Use Bash with `git status`, `git diff`, `git log`, and `git show`; use `rg --no-config` for working-tree search and `read` for files. For revisions not checked out, inspect with `git show` and pipe its output to `rg --no-config` as needed. Working-tree reads do not show another revision. Stay within the available inspection tools; do not fetch refs, check out revisions, run fixes, or bypass restrictions.

### Correctness, security, and operations

- Trace error handling, boundary validation, data-loss risks, cleanup, cancellation, concurrency, and atomicity. Check backpressure, resource bounds, and partial failure on material paths.
- For changed exception handlers and fallbacks, identify what can fail and why recovery belongs at that layer. Prefer propagation or explicit boundary translation when local recovery cannot preserve correctness. Flag hidden failures or false success, not justified recovery. Check use of stable error codes rather than fragile message matching.
- Trace attacker-controlled input to consequential sinks. Verify authorization, feature-gate and internal-only boundaries, parameterized SQL, output escaping, redirect destinations, and protections against user-supplied URLs reaching private resources through DNS or redirects. Report security findings only with a plausible medium-or-higher impact and a concrete attack path.
- Check compatibility, migrations, dependency changes, and local build/run workflows: secrets, environment variables, ports, and newly required setup. Distinguish optional workflows from requirements that break existing users.
- Assess whether tests protect realistic changed invariants and regressions. Identify the missed behavior; do not demand tests merely to increase coverage.

### Structure, ownership, and APIs

Compare the implementation with the simplest viable approach. Look for behavior-preserving changes that delete whole categories of complexity, not merely rearrange them:

- scattered feature checks, ad-hoc branches, flags, or nullable modes that obscure valid states;
- duplicate behavior, bespoke helpers instead of reuse, or feature logic outside its canonical owner;
- thin wrappers, pass-through layers, or generic machinery that add indirection without clarifying a contract;
- unnecessary casts, optionality, or loosely shaped data that hide invariants;
- file growth that harms cohesion or navigation, and coupling that makes a concrete future change span unrelated modules;
- avoidable sequential orchestration or partial updates that make independent work or related state harder to manage safely.

Prefer deleting concepts, clarifying ownership, reusing canonical behavior, and making invalid states harder to express. Consider broader restructuring when it removes substantial complexity and its compatibility and migration costs are justified. Do not demand extraction to meet an arbitrary line limit or introduce an abstraction without a concrete invariant.

Evaluate public APIs from the caller's perspective: discoverability, misuse resistance, error semantics, configuration burden, compatibility, and evolution. Use repository conventions and relevant industry practice where they resolve a concrete problem, not as rules to impose mechanically.

## Finding Bar

Report discrete, actionable issues the author would likely fix. Require evidence, not unstated assumptions about intent or hypothetical downstream breakage. A maintainability finding must name the concrete future change, failure risk, or recurring reasoning cost and explain how the proposed direction reduces it.

Do not flag a deliberate, well-constrained behavior change merely because it differs from the old behavior. Still report unintended consequences, missing safeguards, or serious risks beyond the stated intent. Match severity and required rigor to actual impact and the repository's constraints.

Omit style preferences, cosmetic naming, speculative redesigns, generic requests for more tests, compiler or linter diagnostics, documentation-only concerns, and unrelated pre-existing problems. A cleaner alternative alone is not a finding.

## Report

Return one complete report for `/end-review`. Put findings first, ordered by severity, with a priority tag in each short imperative title:

- [P0]: critical, immediate widespread harm; reserve for unconditional release or operational blockers.
- [P1]: high, likely serious failure or vulnerability.
- [P2]: medium, concrete incorrect behavior or substantial maintenance risk.
- [P3]: low, bounded but actionable defect.

For each finding, give the narrowest useful changed-file line range, concrete impact and triggering conditions, supporting evidence, and a safe correction direction. Keep the explanation to one concise paragraph; use at most three lines of code when needed. Be direct and matter-of-fact; do not exaggerate severity or add praise. Do not produce a full patch or a speculative alternative-architecture section.

End with a concise verdict. State material verification gaps rather than claiming a complete review. If the review is complete and no issue meets the reporting bar, return exactly:
